# 核心算法与跨模块调用

## URL 规范化与条目 ID

`utils.canonicalize_url()`：

1. 去除首尾空白；
2. 将 HTTP(S) 统一为 HTTPS；
3. 主机小写并移除 `www.`；
4. 合并重复 `/`，移除非根路径尾部 `/`；
5. 删除 Fragment；
6. 删除以 `utm_`、`guce_`、`guccounter`、`ref`、`source` 开头的查询参数；
7. 保留其余查询参数。

`url_for_source_filter()` 只移除跟踪参数，不改变 scheme、host 和 path 形状，用于匹配来源正则。

`item_id(source_id, canonical_url)`：

```text
source_id + "-" + sha256(source_id + "|" + canonical_url)[:12]
```

同一文章在不同来源可有不同 ID；Monitor Cluster 负责跨来源关联。

变更 URL 规则会影响去重、历史引用、语义指纹和 Cluster，应先用旧 Fixture 评估迁移影响。

## Feed 发现、解析与缓存

`feeds.discover_feed_urls()` 从 HTML 的 `<link rel=alternate>` 和常见 Feed 链接发现候选。`parse_feed_document()`：

- 识别 RSS/Atom；
- 有界读取 Entry；
- 解析标题、链接、描述、发布时间、图片和 Provider；
- 把相对 URL 解析到 Feed URL；
- 复用 SourceConfig 的过滤和 taxonomy；
- 生成 `ArticleItem`。

`fetch_feed()` 使用 Feed URL Hash 定位缓存，并维护：

- ETag；
- Last-Modified；
- 最近检查/成功时间；
- 下次刷新时间；
- 状态、错误和缓存条目。

304 使用缓存条目；429 读取 `Retry-After`；失败缓存不能转换为成功空 Feed。

## Monitor 合并

`monitor.refresh_monitor()` 分两个阶段：

1. 异步 Feed Phase；
2. 对无 Feed 条目的通用来源执行静态 HTML Fallback。

每来源合并：

- Feed 与 HTML 条目按规范 URL 去重；
- 保留公开发布时间、摘要和图片；
- 当前采集结果与 `max_age_hours` 内历史合并；
- 来源记录保留方法、Feed 结果、错误和 stale；
- Health 更新最近状态、条目数和方法。

Snapshot 是单个原子可变文件。`fresh_monitor_snapshot_path()` 只有在以下条件满足时返回：

- 时间可解析且不在未来五分钟之外；
- 年龄不超过 `snapshot_max_age_minutes`；
- `token_usage == 0`；
- `sources` 与 `items` 是数组。

正式 Run 可复用 Snapshot，但仍独立采集核心 Index；Monitor 异常不污染正式来源状态。

## 确定性跨来源聚类

`clustering.lexical_tokens()` 对标题进行标准化和词元化，`lexical_vector()` 使用稳定 Hash 构造 512 维稀疏向量。

候选对来自：

- 相同规范 URL；
- 共享词元的倒排索引；
- 标题包含关系。

合并前约束：

- module 相同；
- 有时间时相差不超过 96 小时；
- 非相同 URL 至少共享两个词元；
- 余弦相似度达到阈值，或满足包含匹配。

Cluster 使用 Union-Find 合并。旧 Cluster 的成员存在时复用最小旧 `story_id`；否则对代表标题 Hash 生成新 ID。

阶段：

```text
单来源 → new
两来源 → developing
三来源及以上 → confirmed
旧簇增加条目 → updated
```

重要性由 Tier、来源角色、交叉来源数、七日内新鲜度、严重性词和新颖性组成，封顶 100。该分数只用于 Monitor 排序，不直接成为 Report Brief 重要性。

## 正式索引预取与浏览器回退

`prefetch.prefetch_browser_pages()` 对 `browser_index` 来源执行：

1. `httpx` 条件外的普通并发请求；
2. 有界读取响应；
3. 惰性 HTML 解析；
4. 链接、邻近时间、摘要和图片提取；
5. 访问限制分类；
6. 通用 Adapter 生成 `SourceResult`。

`page_needs_browser()`：

- HTTP 已成功获得候选：不回退；
- `rate_limited`：本轮不回退；
- 明确的不可受益 HTTP 失败：不重复；
- 无预取结果、401/403、JavaScript 空壳或专用 Adapter：可回退。

正式预取并发使用 `collection_global_concurrency` 和 `collection_per_domain_concurrency`。

## 来源页合并

`collector.py` 对一个来源的多个入口：

- 规范 URL 去重；
- 按页面轮转候选，避免首个栏目耗尽 `max_items`；
- 任一入口成功且其他失败时保留 `partial`；
- 访问失败优先于 `no_items`；
- `page_results` 保存逐入口诊断；
- 根级 `items` 是规范数组，嵌套 `sources[].items` 为兼容视图。

Index 使用 Revision 不可变保存。Import 与验证合并也必须生成新 Revision。

## 正文 HTTP 优先管线

`content._ordered_targets()` 保留调用者 ID 顺序、忽略重复/未知 ID，再应用硬上限。

HTTP Phase：

- 共用 `httpx.AsyncClient`；
- 有界读取最多 4 MiB；
- 只接受 HTML/XHTML/文本；
- BeautifulSoup 移除脚本、样式、导航、页脚、广告和 Cookie 噪音；
- 依次尝试来源 selector、`article`、`main`、`body`；
- 1500 字符以上为 `full_text`，500—1499 为 `partial`；
- 更短正文保留 `metadata_only`，并判断浏览器是否可能增加价值。

Browser Phase 只接收 HTTP 阶段返回的可受益条目，使用专用 Profile 和更严格的全局/同域并发。

成功正文写为带 Frontmatter 的 Markdown。新 Index Revision 更新：

- `content_status`；
- `content_path`；
- 字符数；
- 获取方式、selector、HTTP 状态和错误。

`synchronize_nested_items()` 同步兼容嵌套视图。

## Context 压缩

`context._compact_candidates()` 按来源分组，排序：

1. `full_text/partial`；
2. 有可解析发布时间；
3. 发布时间新；
4. 原来源排名。

基础上限：

```text
min(context_items_per_source, max(5, report_target * 2))
```

已富化条目不会因基础上限被截掉。每个候选增加：

- `source_candidate_rank`；
- `source_rank`；
- `previously_reported`；
- `semantic_fingerprint`。

Context 只保留写作需要的字段，并加入最近报告、Evaluation、活跃 Thesis、Watchlist、Prediction 和用户反馈。

## 语义缓存

`semantic_fingerprint()` 绑定条目身份和证据内容。`reusable_semantic_brief()` 只有在以下条件满足时返回：

- 指纹不变；
- 上次 Evaluation 允许复用；
- 没有排除 `event_summaries` 或全部内容；
- 缓存字段结构有效。

可复用 Brief 进入 Context，减少重复写作；证据变化后必须重新写。

## Brief Plan 与批次

`_balanced_source_batches()`：

1. 统计每来源候选数；
2. 按候选数降序；
3. 把整个来源放入当前条目最少的批次；
4. 最多三个批次；
5. 同一来源不跨批次。

`_build_brief_plan()`：

```text
target = min(
  候选数,
  source.report_target,
  source.report_max,
  15
)
```

每个 Plan 保存：

- 来源和目标栏目；
- Batch ID；
- `default_item_ids`；
- `reuse_item_ids`；
- `author_item_ids`。

发现来源 target 为 0，不产生 Brief Plan。

## Packet 与批次验收

每批 Packet 明确：

- 不可信数据声明；
- 允许读取的候选和正文；
- 允许写入的唯一 Draft 路径；
- 允许执行的唯一提交命令；
- 必填字段和一次修复策略。

`validate_authoring_batch()` 检查：

- 所有分配 ID 恰好出现一次；
- 无额外 ID；
- 翻译和 TL;DR 符合 run 的目标语言；
- 重要性范围；
- 生命周期状态。

`submit_authoring_batch()` 验证输入路径必须等于 Packet 指定路径，通过后写不可变 Receipt。Session Context Hash 或 Run attempt 不匹配时拒绝混用。

## 分析包

`prepare_analysis_packet()`：

1. 合并语义缓存与批次 Receipt；
2. 按 Plan 建立七个栏目；
3. 记录缺失批次和有效覆盖目标；
4. 写 `brief-skeleton.json`；
5. 从已完成 Brief 中按重要性选最多 18 个候选；
6. 附加已有正文路径、连续报告、Thesis、Watchlist、Prediction 和反馈；
7. 写 `analysis-packet.json`。

主模型从候选中选择通常 6—10 个 Featured Event，写三个分析域和一次跨视角综合。它不能重新生成全部 Brief。

## schema 2.0 装配

`assemble_report_draft()`：

- 读取 Session Skeleton；
- 验证 Analysis Result 路径在数据根内；
- 只接收规定顶层键；
- 把 Featured Event 归入对应栏目；
- 合并三分析域与综合；
- 保留显式降级信息；
- 写 `report-draft.json`；
- 将 Session 标为 `ready`。

当前 Context 为 2.0 时，`workflow._require_current_context_schema()` 拒绝 1.5 草稿。

## 报告编译

`reporting.compile_report_data()` 是模型语义进入持久 Report 的唯一编译入口：

1. 设置当前 schema、语言、日期和生成时间；
2. 归一化栏目与旧别名；
3. 删除未知、重复或错误栏目的 Brief；
4. 从 Index 注入标题、URL、来源、时间和访问状态；
5. 生成稳定 Event ID 和来源引用；
6. 绑定图片与来源排名；
7. 规范三域 Analysis 引用；
8. 规范 Synthesis 事件引用；
9. 从 Index 生成待验证来源；
10. 计算计数、来源指标和警告。

编译器不会翻译标题、编写 TL;DR、生成缺失 Brief、补写研判或把未知 ID 模糊匹配到相似文章。

## 报告校验

`validate_report_data()`：

1. JSON Schema；
2. 报告内部跨字段；
3. Report 与 Index 证据身份；
4. 覆盖目标与连续状态。

关键检查：

- 七栏目与三分析域完整；
- schema 2.0 分析协议和综合完整；
- 用户可见文本符合 `zh-CN` 或 `en`；
- 原题与 `title_zh` / `title_en` 译题分离；
- 禁止访问占位和伪 TL;DR；
- 来源 ID、标题、URL、时间、access 一致；
- Brief 覆盖和每来源上限；
- Featured Event 最多 12，单事件单来源文章；
- Analysis/Synthesis 只引用已有 Event；
- 具名来源绑定；
- `NEW` 的发布时间；
- 数字情景的 `scenario_basis`；
- 晚报变化与观察项；
- Evaluation 的 ID、Hash、总分和连续性决定。

Error 阻止保存；Warning 随 Artifact 返回。`validate-report` 本身不写 Report 或分配 Revision。

## 保存与投影

`reports.save_report()`：

1. 编译与预校验；
2. 下载/绑定公开图片；
3. 最终校验；
4. 分配 Report Revision；
5. 保存不可变 JSON/Markdown；
6. 更新 `latest-{edition}.json`；
7. 调用 `write_local_outputs()`；
8. 更新语义缓存待评记录与派生状态；
9. 返回 Artifact 和分阶段耗时。

`local_output.write_local_outputs()`：

- HTML 文本转义，远程外链只允许 HTTP(S)；
- 本地 Report HTML 使用相对媒体路径；
- 桌面 HTML 使用绝对 `file:///` 媒体、归档和 PDF 路径；
- 桌面文件名包含日期、edition 和 Revision；
- 日报索引扫描本地 Report/Evaluation 重建；
- PDF 优先配置引擎，Edge 失败回退 ReportLab；
- 投影错误不会删除 JSON/Markdown。

## 前台 Finalize 与后台 Tail

`finalize_edition(..., defer_tail=True)`：

- 前台保存 JSON/Markdown/HTML/桌面 HTML；
- Run 进入 `completed` / `completed_partial`；
- Tail 记录请求格式、Notion 选项和恢复命令。

`complete_edition_tail()`：

- 要求 Run 已本地完成；
- 按锁串行；
- 已完成直接返回；
- 缺 PDF 才生成；
- 未发布且请求 Notion 才发布；
- 未有有效调度才安排 Evaluation；
- 独立记录 `completed/partial`。

## Notion 发布

`notion.publish_report()`：

1. 读取 Token 与 Data Source ID；
2. 获取目标 Schema；
3. 选择完全匹配的 Profile；
4. 验证 Report；
5. 按日期/edition 查找或创建页面；
6. 上传或复用图片；
7. 按 Registry 的 `blocks_appended` 续传；
8. 更新页面属性和完成状态。

Evaluation 通过同一 Registry 定位页面。Notion 内容不参与 Report 编译或连续状态事实。

## Evaluation 与连续状态

`reports.save_evaluation()`：

1. 校验独立角色、Report ID 和 Hash；
2. 保存不可变 Evaluation；
3. 更新 `evaluations/latest-*`；
4. 根据 Evaluation 决定语义缓存可复用范围；
5. 更新事件、Thesis、Watchlist、Prediction；
6. 重建 HTML、桌面 HTML 和 PDF；
7. 更新对应 Run 的 Evaluation/Artifact。

低分或 `reject` 只阻止后续语义复用，不修改原 Report。

| 修改 | 同步检查 |
| --- | --- |
| URL 规范化 | ID、去重、旧 Index、语义指纹、Cluster |
| Feed 解析 | 缓存、Monitor 状态、发布时间、图片 |
| 聚类 | 稳定 story、阶段、重要性、Dashboard |
| 来源过滤 | SourceConfig、Adapter、Normalize 测试 |
| 状态枚举 | Collector、Monitor、Importer、Verification、Report |
| Context 排序 | Brief Plan、缓存复用、覆盖 |
| Authoring | Packet、Receipt、截止、指标、装配 |
| Report 字段 | Schema、模板、编译、校验、所有投影 |
| Analysis 协议 | Packet、Synthesis、Evaluation、连续状态 |
| 图片 | DNS、缓存、HTML/PDF、Notion |
| Artifact 路径 | Runtime Guard、恢复、安装器、忽略规则 |
| 桌面投影 | OutputConfig、绝对链接、失败测试 |
| Publisher | Schema、Registry、续传、Tail 恢复 |
